# Android ships as a thin client that writes intents, not rows

**Status:** Proposed · 2026-09-14

Android is a standalone Kotlin + Compose client, not a mobile target of the existing Tauri app and not a React Native port sharing code with the desktop UI. It reads the synced database over HTTP and writes nothing to it. Every change the user makes on the phone is appended to a separate outbox database as an intent — *set job 42 to Application Sent at time T* — which the desktop drains and applies by calling its existing functions (`create_job`, `update_job`, `update_job_status` in `db.rs`, all plain `pub fn` taking an `AppHandle`).

**Why:** Reusing the Tauri shell looks free and is not. Roughly half of the 59 commands are desktop-bound — Python sidecar spawn, OS keyring, `rfd` file dialogs, the `open` crate, desktop path resolution — and the Kanban and table views are laid out for a desktop window.

Writing intents rather than rows solves two problems at once. It keeps the desktop the single writer to the synced database, which is what ADR 0006 depends on. And it means the write logic is never duplicated: the Tauri commands are not thin SQL wrappers, and applying intents through them preserves every invariant automatically — `update_job_status` writes its `status_history` row in the same transaction, `update_job` validates non-empty company, bumps `updated_at`, and appends `status_history` when the status changed, and `delete_job` hand-cascades to `job_documents` and `status_history` before removing files from disk. The schema declares no foreign-key cascades; that cascade exists only as Rust code. A phone writing raw SQL would silently skip all of it.

**Considered options:** Tauri v2 Android reusing the React UI; React Native + Expo sharing contracts with the desktop (the earlier roadmap's recommendation), which still needs the whole backend reimplemented and adds a second JS toolchain; a phone writing directly to the synced tables, which duplicates the invariants above in Kotlin and forfeits the single-writer property; native Kotlin + Compose writing intents. Chose the last. The Kotlin/Java libSQL SDK is less mature than the Rust and TypeScript ones, so Turso's HTTP API via Ktor is the default transport.

**Consequences:** Delete is shippable on Android after all, since the desktop performs the cascade — the phone only records the intent. Scope stays deliberately narrow regardless: view jobs, change status, edit text fields and dates, create a job by hand, delete. No capture, no mail scan, no LLM extraction, no calendar, and no attachments, all of which are desktop-only by design (ADRs 0001, 0002, 0004) or live on the filesystem rather than in the database.

The cost is latency and a UI obligation. A phone edit does not take effect until the desktop next runs, so the Android client must show its own unapplied intents optimistically and distinguish them from confirmed state; a job created on the phone has no real integer id until the desktop assigns one. Intents carry client-generated UUIDs so they can be matched up afterwards. Applying an intent is last-write-wins by timestamp, with the desktop as the serialization point. The phone needs connectivity to record an intent at all; a local queue that replays on reconnect is deferred to a later version.
