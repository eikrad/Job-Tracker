# Android ships as a separate thin client, not Tauri mobile

**Status:** Proposed · 2026-09-14

Android is a standalone client that talks to Turso directly over HTTP (ADR 0006), not a mobile target of the existing Tauri app and not a React Native port sharing code with the desktop UI. Scope is deliberately narrow: view jobs, change status, edit text fields and dates, create a job by hand. No capture, no mail scan, no LLM extraction, no calendar, no attachments, and no delete.

**Why:** Reusing the Tauri shell looks free and is not. Roughly half of the 59 commands are desktop-bound — Python sidecar spawn, OS keyring, `rfd` file dialogs, the `open` crate, desktop path resolution — and would each need feature-gating, while the Kanban and table views are laid out for a desktop window. A thin client skips the entire Rust backend and targets the synced schema directly. The excluded features are already desktop-only by design (ADRs 0001, 0002, 0004), so omitting them costs nothing the product was promising.

**Considered options:** Tauri v2 Android reusing the React UI; React Native + Expo sharing contracts with the desktop (the earlier roadmap's recommendation), which still needs the whole backend reimplemented and adds a second JS toolchain; a read-only viewer over a one-way mirror; native Kotlin + Compose, remote-only. Chose native Kotlin + Compose. The Kotlin/Java libSQL SDK is less mature than the Rust and TypeScript ones, so Turso's HTTP API via Ktor is the default transport.

**Consequences:** Write invariants currently enforced in Rust must be reimplemented client-side, because the phone bypasses the Tauri commands entirely: `update_job_status` writes a `status_history` row in the same transaction; `update_job` validates non-empty company, bumps `updated_at`, and appends `status_history` when the status changes as a side effect; `delete_job` hand-cascades to `job_documents` and `status_history` and then removes files from disk. The schema declares no foreign-key cascades — the cascade is Rust code — so a raw `DELETE FROM jobs` from the phone orphans rows in two tables and leaks files on the desktop. Status change and field edit are reimplemented as batched transactions over the HTTP API; delete is not shipped on Android. The phone requires connectivity to save; an offline outbox of pending mutations replayed on reconnect is deferred rather than solved by switching libSQL to offline writes, which ADR 0006 rejects.
